# i18n/Translations rule

**CRITICAL: Always add translations immediately when adding labels**

## Translation sources

The Primebrick i18n system has **two sources**:

1. **Backend (BE)** — the primary source for ALL translations. The BE serves
   translations as a flat dict (dot-path keys → string values) via the i18n
   API. The FE merges these at runtime via `mergeModuleDict()`. Keys under
   `system.*`, `entities.*`, `shell.*`, and any other non-`app.*` namespace
   come exclusively from the BE.

2. **FE fallback** (`src/lib/i18n/messages/en-GB-fallback.json`) — a flat
   JSON file containing **English-only** translations for keys in the
   `app.*` namespace. This is used when the BE is unreachable (e.g. login
   pages, error pages, public routes). It is NOT a complete dictionary —
   it only covers keys needed before authentication.

### Rules

- **ALL translations are owned by the BE.** When adding a new label, the
  translation key and value MUST be added to the BE's translation system.
- **FE fallback is ONLY for `app.*` keys.** If a new `app.*` key is added,
  it MUST also be added to `en-GB-fallback.json` (English only).
- **Non-`app.*` keys MUST NOT be added to the FE fallback.** They are BE-owned.
- **The FE fallback is English-only.** Never add Italian, French, German,
  Spanish, or Portuguese translations to the FE fallback file.
- **When adding a label to a component**, add the translation key to the BE
  immediately. If the key is under `app.*`, also add it to
  `en-GB-fallback.json`.
- **Never hardcode user-facing text** in components. Always use `$t('key')`.

## Key convention

- Translation keys MUST be `snake_case` singular (see
  `.devin/rules/translation-key-convention.md` for the full convention).
- Keys are flat dot-paths (e.g. `system.settings.config.typeConfig.minLength`).
- The FE dict is flat — `Object.keys($dict)` returns all available keys.

## Example

```svelte
// Component
<p>{$t('system.settings.config.typeConfig.minLength')}</p>
```

```json
// src/lib/i18n/messages/en-GB-fallback.json (ONLY if key is app.*)
{
  "app.auth.login.title": "Sign In"
}
```

```ts
// BE translation system (ALL keys, ALL languages)
// Added via BE i18n management, not in FE code
```

## Modules and the `custom` schema

- `app.*` keys live in `public.translations`; `system.*` keys in
  `system.translations`; module namespaces map to their own schema.
- **`custom.translations`** holds user-created keys — global, shared across
  orgs, authenticated-only. Custom keys MUST start with `custom.`; other
  modules reject `custom.*` keys (enforced BE-side on create/update).
- Load order after login/reload: `app` → `custom` → route module lazily,
  all via localStorage + ETag revalidation.

## UiLang ↔ dictionary parity (MANDATORY)

Every entry in `UI_LANGS` (`src/lib/i18n/languages.ts`) and every row in the
`LangSelect` dropdown MUST have a real dictionary in the BE translations
tables. `normalizeLang()` matches exact tags FIRST (`en-US` stays `en-US`),
and only falls back to the primary subtag (`en` → `en-GB`) for UNLISTED
tags — so a listed language with no dictionary produces empty dicts and the
deliberate raw-key display kicks in everywhere.

This actually happened: `en-US` was offered in the selector but the DB only
shipped `en-GB` (+ 5 others). Fixed by seeding `en-US` from `en-GB`
(`db-meta/fire-and-forget/seed_en_us_translations.sql` in the BE repo —
Redis `translations:i18n:*` must be invalidated afterwards).

- Adding a `UiLang` without seeding its dictionaries is a bug, not a partial
  feature — raw keys will render for every `system.*`/`app.*` label.
- Removing a language's dictionaries without removing the `UiLang` is
  equally a bug.
- E2E check: for each offered language, `fetchModuleTranslations` must
  return a non-empty dict.

## Entity write payloads — `{entity, translations?}` standard

ALL non-bulk single-entity CUD calls to `/api/v1/entities/*` (BE and `/ws/`
microservice proxies) use the `EntityWritePayload<E>` envelope from
`$lib/api-types`: entity fields under `entity`, optional `translations`
sibling. Flat bodies are rejected with `400`. Bulk endpoints (`bulk-*`,
`duplicate`, `restore`), RPC endpoints and `DELETE` are exempt. See
`.devin/rules/entity-write-payload.md`.

## Pending translations — atomic entity writes

Translation rows created during a form flow (e.g. the Smart JSON assistant's
key_picker) MUST NOT be inserted before the owning entity is saved. Use
`$lib/i18n/pending-translations.svelte`:

- `addPendingTranslation(key, { lang: value })` — queue rows.
- `takePendingTranslations()` — drain into `{ key, language, value }[]` and
  append as `translations` in the entity create/update payload; the BE
  inserts them in the SAME transaction (`{ entity, translations }`). The
  `translations` sibling requires `TRANSLATIONS_MANAGE` on the BE.
- `clearPendingTranslations()` — on page destroy/cancel so nothing orphaned
  reaches the DB.
